# ADR-0004: SHA-256 для партнёрских API-ключей

## Контекст

Первый план предполагал Argon2id или bcrypt и переменную `API_KEY_HASH_COST`. Это вроде неплохая стратегия для пароля, который человек выбирает сам. Такой пароль нужно подобрать, поэтому проверка обязана быть медленной.

Партнёрский ключ устроен иначе. Это длинный случайный токен (~256 бит энтропии), его выпускает платформа, а не заведение. Проверять его приходится часто: синхронизация меню, поллинг очереди раз в несколько секунд, команды по заказу. Медленный KDF на каждый такой запрос — искусственная нагрузка, которая ничего не добавляет к стойкости.

## Решение

В базе храним SHA-256 от полного ключа и восьмисимвольный префикс, по которому находим запись одним индексным чтением. Сравнение хеша — constant-time (`subtle.ConstantTimeCompare` / `hmac.Equal`). Сам секрет после выпуска больше не показываем и не логируем.

Переменная `API_KEY_HASH_COST` не нужна и из конфига убрана.

Кэш префикса в памяти с TTL около 30 секунд снимает лишние походы в Postgres на горячем пути. Отзыв ключа действует с этой задержкой — это компромисс.

## Следствия

Проверка ключа стоит микросекунды и не спорит с rate limiter'ом за CPU. Утечка таблицы хешей по-прежнему плоха, но ключ нельзя «подобрать как пароль». Зато его можно отозвать, а префикс помогает найти нужную строку, не сканируя всю таблицу.

Если понадобится enterprise-интеграция, следующий шаг — ротация, секрет в менеджере секретов и OAuth2 `client_credentials`. Менять алгоритм хеша паролей для этого не требуется.
