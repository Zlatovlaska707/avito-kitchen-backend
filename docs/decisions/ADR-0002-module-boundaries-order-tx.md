# ADR-0002: Границы модулей и транзакция создания заказа

## Контекст

Правила слоёв простые: usecase не пишет SQL, репозиторий не импортирует соседний репозиторий. На создании заказа эти правила встречаются с реальностью.

Оформить заказ — значит в одном атомарном шаге:

- прочитать корзину и актуальные цены меню;
- проверить, что заведение открыто, адрес в зоне, чек не ниже минимума;
- записать заказ со снимком состава;
- пометить корзину `converted`;
- сохранить ответ идемпотентности;
- положить `order.placed` в outbox.

Если хотя бы один из этих шагов уедет в соседний `COMMIT`, покупатель может получить заказ без события для кухни — или наоборот.

## Решение

Модули по-прежнему владеют таблицами: `venues`, `catalog`, `cart`, `ordering` не ходят в чужие схемы напрямую. Исключение одно и явное: usecase `ordering/create`.

Он открывает транзакцию через `go-transaction-manager` и вызывает контракты репозиториев `cart`, `catalog`, `order`, `idempotency`, `outbox`. Каждый репозиторий исполняет SQL только к своим таблицам, но в общем `tx`, который едет в `context`. Прямого `SELECT` из `order`-репозитория в `menu_items` нет.

Так атомарность есть, а владение данными остаётся на уровне пакетов, а не «всё в одном main-репозитории».

## Следствия

Снимок цен и состав заказа согласованы с корзиной: либо всё записалось, либо ничего. Проще проверить, что SQL не протекает через границы.

Цена: `ordering/create` знает больше соседей, чем типичный сценарий вроде «получить меню». Это сознательная концентрация сложности в одном месте, а не расползание join'ов по всем репозиториям.

Если модули когда-нибудь разъедутся по сервисам, эту транзакцию придётся заменить сагой. Outbox уже готов быть границей (ну в теории): событие уезжает наружу после локального коммита.
