# ADR-0001: Модульный монолит

## Контекст

Нужно закрыть три HTTP-слоя/поверхности (покупатель, заведение, администратор), фоновые задачи, доставку вебхуков и симулятор POS.

Микросервисы здесь выглядят солидно, но главный сценарий — оформление заказа — требует атомарности: проверить стоп-лист, зафиксировать цены, создать заказ, закрыть корзину, записать событие для заведения. Если это разные базы и разные деплои, появляется сага с компенсациями. Для MVP это лишняя сложность.

## Решение

Один Go-процесс: модульный монолит. HTTP API и воркеры живут в одном бинаре, воркеры ходят в Postgres отдельным пулом соединений.

Границы пакетов жёсткие: `handler → usecase → contract ← infrastructure`. Модуль владеет своими таблицами и не читает чужие в обход контракта.

Единственный второй deployable в репозитории — `venue-simulator`. Его отдельность требует задание, и он общается с платформой только по публичному Partner API.

## Следствия

Деплой сводится к `docker compose up`. Checkout — одна транзакция, без распределённого согласователя. Операций меньше: один сервис, один конфиг, одни логи.

Масштабировать инстанс можно только целиком. Если поднять несколько реплик API как есть, воркеры начнут дублировать работу — понадобится либо лидер, либо вынос воркеров. Для одной реплики MVP это приемлемо.

Когда появятся разные профили нагрузки, вот тогда швы начнут проступать: каталог (много чтения) и consumer outbox (медленные HTTP) — будут первые кандидаты на отдельный сервис.
